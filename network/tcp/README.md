# tcp — 信頼できるバイトストリーム

**信頼できないパケット網の上に、信頼できて順序どおりのバイトストリームを作る**——
TCP の肝を Go でモデル化する。ネットワーク下層編のパーツ。実ソケットを使わず、
損失・並べ替えのある網と、その上で信頼性を回復する仕組みを決定的に再現する。

教科書の章: [tcp](https://sharin-2a1.pages.dev/parts/tcp)

## これは何か

下層の IP は、パケットを**届く保証も順序の保証も無く**運ぶだけだ——落ちる・遅れる・
入れ替わる。にもかかわらず、アプリからは「書いた順にそのまま届く 1 本のバイトの管」に
見える。この錯覚を作るのが TCP だ。道具立ては次の 5 つ:

1. **3-way ハンドシェイク**(SYN / SYN-ACK / ACK): 接続を確立し、両者の初期シーケンス番号を同期
2. **シーケンス番号 + 累積 ACK**: 送る各バイトに通し番号を振り、受信側は「ここまで連続で
   受け取った」を ACK で返す
3. **再送**: ACK が返らないバイトを、タイマ満了で送り直す = 信頼性の中核
4. **スライディングウィンドウ**: 未確認のまま送ってよい量に上限を設ける = フロー制御
5. **並べ替え**: 順序が乱れて届いても、受信側が連続する先頭から順にアプリへ渡す

```
   アプリから見た TCP: 順序どおりの 1 本のバイトストリーム
   ┌───────────────────────────────────────────────┐
   │  H E L L O   T C P                             │
   └───────────────────────────────────────────────┘
                    ▲ この錯覚を、下の乱れた網の上で作る
   ┌───────────────────────────────────────────────┐
   │ IP: パケットは落ちる・遅れる・入れ替わる       │
   │   [seq101] [seq105]✗落 [seq109] …→ 再送で回復   │
   └───────────────────────────────────────────────┘
```

## 肝は3つ

1. **信頼性 = seq + ACK + 再送**: 番号で「どこまで届いたか」を突き合わせ、抜けたら送り直す
2. **順序 = 受信側の並べ替え**: 乱れて届いても、累積 ACK は連続の先頭までしか進めない。
   隙間が埋まるとまとめてアプリへ渡す
3. **フロー制御 = ウィンドウ**: 相手が受け取れる量(広告ウィンドウ)を超えて送らない

## ファイル

- `tcp.go` — `Endpoint`(接続の片側の状態機械)。`State`(CLOSED/LISTEN/SYN_SENT/…/
  ESTABLISHED/…)、`Segment`(seq/ack/flags/window/payload)、送信側(seq・ウィンドウ・
  再送タイマ)と受信側(並べ替えバッファ)のロジック
- `sim.go` — `Sim`(パケット網の模擬)。2 エンドポイントを繋ぎ、離散ステップで進める。
  特定セグメントを落として損失と再送を決定的に再現する

## 設計メモ

- **SYN と FIN は seq を 1 消費する**: 制御フラグもシーケンス空間の 1 バイトとして扱う——
  だから「SYN が確かに届いた」ことを ACK 番号で確認できる。実機の TCP と同じ約束
- **累積 ACK**: ACK は「次に期待するバイト番号」。連続して受け取った先頭までしか進めないので、
  抜けが 1 つあると、その後がいくら届いても ACK は進まない → 送信側は抜けを送り直す
- **go-back-N 風の再送**: 再送タイマが満了したら、未確認の先頭(`sndUna`)まで巻き戻して送り直す。
  受信側は先行して届いた分を並べ替えバッファに退避してあるので、隙間が埋まればまとめて渡る
- **決定的な損失**: 送出順の通し番号で「この番号のセグメントを落とす」と指定できる。乱数を
  使わないので、再送の様子を毎回同じに再現できる(テスト・デモが安定する)

## 簡略化したこと

- **輻輳制御なし**: スロースタート・輻輳回避(cwnd)・高速再転送/回復は実装しない。ウィンドウは
  相手の広告値(フロー制御)のみで、ネットワークの混雑には反応しない
- **タイマは固定 RTO**: RTT 計測に基づく適応的タイムアウト(Karn/Jacobson)は無し。固定ステップ
- **データは一方向**: クライアント→サーバの転送に絞る(双方向同時送信は割愛)。ハンドシェイクと
  クローズは両方向
- **1 パケット = 1 セグメント、小さい MSS**: 教材用に MSS を 4 バイトにして、複数セグメントの
  やり取りが短いデータでも起きるようにしている
- **チェックサム・実ヘッダ・ポート/IP なし**: 誤り検出や実際のヘッダ整形、多重化(ポート)は扱わない。
  信頼性・順序・フロー制御の骨格だけを取り出す
