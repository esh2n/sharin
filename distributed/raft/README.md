# distributed/raft

Raft 合意アルゴリズムの最小実装。分散システム編の核。
複数ノードが「ログの並び」に合意し、一部が壊れても止まらない仕組みをフルスクラッチで作る。

## 肝

- **純粋状態機械**: ノードは `Step(Message)` と `Tick()` だけで動く。内部で時計も通信も
  持たない。だからテストが完全に決定的で、選挙の競合も分断も1プロセスで再現できる
  (etcd/raft と同じ設計)。時間の経過すら外から `Tick()` で刻む
- **安全性は「多数決 + ログの新しさ」**: リーダーになれるのは自分以上に新しいログを持つ者だけ
  (古い者を選ばない)。確定(commit)は過半数に複製された位置まで、かつ現任期のエントリに限る
  (図8: 前任期のエントリを数だけで確定すると後で覆る)
- **PreVote + リーダーリース**: 分断から戻ったノードや外したノードが、無駄に任期を吊り上げて
  正当なリーダーを引きずり下ろす「割り込み」を防ぐ。仮投票で勝てる感触を得てから本番の任期を上げる

## 作ったもの

| 機能 | ファイル |
|---|---|
| リーダー選出(PreVote付き) | `raft.go` (hup/startCampaign/handleVoteRequest) |
| ログ複製と commit 前進 | `raft.go` (sendAppend/handleAppendResp/maybeCommit) |
| ログ抽象(スナップショット圧縮対応) | `log.go` |
| スナップショット送受信 | `raft.go` (Snapshot/handleSnapshot) |
| 単一サーバ構成変更(ノード追加/削除) | `raft.go` (ProposeConfChange/recomputeMembership) |
| 分断を注入できるクラスタ・シミュレータ | `cluster.go` |

## 簡略化したこと

- **ログの永続化なし**: term/vote/log はメモリのみ(実物はディスクに fsync してから応答する)。
  クラッシュ復帰は扱わない。db 編の [WAL](../../docs/parts/wal.md) と接続すればここが埋まる
- **メンバ変更は単一サーバ方式**: 1回に1台だけ。原論文の joint consensus(2構成の重ね合わせ)は
  実装しない。単一サーバ変更なら過半数が分裂しないので安全(Ongaro の学位論文の推奨)
- **クライアント側の重複排除なし**: at-least-once。同じ書き込みが2回適用されうる(実物はセッション+
  シーケンス番号で冪等化する)
- **リーダー移譲・読み取り最適化(ReadIndex/リース読み)なし**: 読みは扱わず書き込みの合意に集中
