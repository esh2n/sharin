# crdt — 順序を決めるのをやめる

[clock](../clock/) の章で、同時に起きた2つを見分けられるようにした。
見分けられると、片方を黙って捨てずに済む。では、捨てないなら何をするのか。

1つの答えが、**まとめ方をあらかじめ決めておく**ことになる。
どちらが先かを決めるのをやめて、2つを1つにする規則だけを用意する。

## 3つの性質

| 性質 | 意味 | これが無いと |
|---|---|---|
| 可換 | `a.Merge(b) == b.Merge(a)` | 届く順で結果が変わる |
| 結合的 | `(a∪b)∪c == a∪(b∪c)` | まとめる括り方で結果が変わる |
| 冪等 | `a.Merge(b).Merge(b) == a.Merge(b)` | 二度届くと壊れる |

3つそろうと、順序も回数も関係なくなる。
[reconcile](../../orchestration/reconcile/) が取りこぼしに強かったのと同じ理屈が、データの側にも現れる。

## 数え上げ

```go
g := crdt.GCounter{}
g.Inc("a", 3)          // 自分の要素だけを増やす
g.Merge(other)         // 要素ごとに大きいほうを取る
```

`GCounter` は[ベクタークロック](../clock/)とまったく同じ形になっている。
あちらは出来事を数え、こちらは値を数えているだけで、まとめ方は同一。

減らす操作は直接持てないので、**減らした量を別の数え上げに足す**。

```go
c := crdt.NewPN()
c.Inc("a", 10)
c.Dec("a", 3)
c.Value()  // 7 = P.Value() - N.Value()
```

[2の補数](../../foundations/numbers/)が引き算を足し算にしたのと同じ発想になる。

## 集合の難しさ

消したことをどう表すかで、性質が変わる。

| 型 | 消し方 | 足し直せるか | 並行な add と remove |
|---|---|---|---|
| `TwoPSet` | 消した集合に入れる | **できない** | remove が勝つ |
| `ORSet` | 見えている印だけ消す | できる | **add が勝つ** |

```go
a, b := crdt.NewOR(), crdt.NewOR()
a.Add("a", "x")
b.Add("b", "x")   // 別のノードが独立に足した
a.Remove("x")     // a に見えている印だけ消える
a.Merge(b).Has("x")  // true ← b の印は見ていないので残る
```

追加ごとに一意な印をつけ、削除は**そのとき観測した印だけ**を消す。
見ていない印は消えないので、並行して足されたものは生き残る。

## 最後を残す形は、片方を黙って消す

```go
a := crdt.LWW{}.Set("東京", 5, "a")
b := crdt.LWW{}.Set("大阪", 5, "b")  // 同じ時刻 = 同時に書かれた
a.Merge(b).Value  // "大阪"(同点はノード名で決まる)
a.Lost(b)         // "東京", true ← 消えたほう
```

まとめ方としては3つの性質を満たすが、消えたことは残らない。
`Lost` は観測用で、実際に何が消えたかを知りたいなら、まとめる前に自分で持っておくしかない。

## API

| 型 | 操作 |
|---|---|
| `GCounter` | `Inc(node, n)` / `Value()` / `Merge` |
| `PNCounter` | `Inc` / `Dec` / `Value()` / `Merge` |
| `LWW` | `Set(v, stamp, node)` / `Merge` / `Lost` |
| `TwoPSet` | `Add` / `Remove` / `Has` / `Values` / `Merge` |
| `ORSet` | `Add(node, v)` / `Remove(v)` / `Has` / `Values` / `Tags` / `Merge` |

`Merge` はすべて新しい値を返す。元は変えない。

## 決定性

実時間も乱数も使わない。`Values` は名前順、印はノード名と連番で一意。
6通りすべての合流順で同じ値になることをテストで固定している。
