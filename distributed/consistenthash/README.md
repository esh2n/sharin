# consistenthash — コンシステントハッシュ法(ハッシュリング)

「どのキーをどのノードに置くか」を決めるシャーディングの土台。ノードの増減で**動くキーを
最小限**にし、**仮想ノード**で負荷を平準化する。

## 肝

- **素朴な `hash(key) % N` の罠**: N が1変わるとほぼ全キーの割り当てが変わる(再ハッシュ地獄)。
  デモ/テストで 4→3 台にすると mod は 3000件中 ~2230件が動く
- **リング**: ノードもキーも円環 `[0, 2^32)` に置き、キーは「時計回りで最初に出会うノード」に属する。
  ノード増減で動くのはその担当弧の分だけ = 平均 K/N 個。同条件で ~1099件しか動かない
- **仮想ノード(vnode)**: 1物理ノードを円環上の多数の点として置き、担当弧の偏りをならす。
  負荷のばらつきはおよそ 1/√(vnode数)。vnode 1個だと max/min 負荷比が数百倍、増やすほど縮む
  (物理3台・vnode 300 でノード名次第で 1.1〜1.4 倍程度。ノードが増えるほどさらに均等に)

## 作ったもの

| 関数 | 役割 |
|---|---|
| `New(replicas, hash)` | リング生成。replicas=物理1台あたりの vnode 数、hash は差し替え可(既定 CRC32) |
| `Add(nodes...)` | ノードを vnode 群として円環に追加(二重登録はスキップ) |
| `Remove(node)` | ノードの点だけ削除(他ノードの割り当ては不変) |
| `Get(key)` | 担当ノードを二分探索(時計回り最初のノード、端は回り込み) |
| `GetN(key, n)` | 時計回りに distinct な n ノード。レプリケーション先の選定に使う |
| `Nodes()` | 登録済み物理ノード一覧 |

ハッシュは **CRC32(IEEE)** を既定に。"node#i" のような似た短い文字列でも点がよく散らばる
(FNV-1a はこの用途だと偏りが大きく、負荷比が 2倍超になった。groupcache も crc32)。

## 簡略化したこと

- 円環は 32bit。実物(Cassandra/Dynamo)は 128bit の広い空間を使う
- vnode 数は全ノード一律。実物は容量差に応じて重み付け(重いノードに多くの点)する
- データの実移動・再バランスは扱わない(所属の計算だけ)。ホットスポット対策(bounded loads)も無し
- レプリケーション先の選定 `GetN` は「時計回りに distinct」まで。ラック分散などの配置制約は無し
