# replication — 単一リーダーのログシッピング複製

リーダー(primary)の書き込みログをフォロワー(replica)へ順番に流し、同じ状態を複製する
最小実装。[wal](../../db/wal/) の「べき等な絶対値レコード」を土台に、**耐久性ポリシー**の
トレードオフを目で見えるようにする。

## 肝

- **耐久性ポリシー**: 書き込みを「確定(クライアントへ ack)」と見なすのに何台の複製を待つか。
  - `Async` — 待たない(1台=リーダーのみ)。速いが、リーダー故障で未複製ぶんが消えうる
  - `Quorum` — 過半数(リーダー込み)。少数の遅い/落ちたレプリカを許容しつつ、昇格先が最新なら無損失
  - `Sync` — 全台。無損失だが、1台落ちると書き込みが止まる
- **複製ラグと stale read**: 遅れたレプリカから読むと自分の書き込みが見えない(`Lag` / `ReplicaValue`)
- **フェイルオーバーのデータ損失窓**: `Promote` で遅れたレプリカを昇格させると、
  未複製の確定済み書き込みが消える。その数を返す(= 損失窓)

## 作ったもの

| 型・関数 | 役割 |
|---|---|
| `Durability` (`Async`/`Quorum`/`Sync`) | 確定に必要な複製数を決める |
| `Record{Offset,Key,Value}` | べき等な1件の書き込み(絶対値で置く) |
| `NewCluster(replicas, d)` | リーダー1台 + レプリカ n 台の複製系 |
| `Write(key,value)` | 書いて到達可能なレプリカへ複製、確定したかを返す |
| `Disconnect`/`Connect` | レプリカを切る/再接続(再接続で一気に追いつく) |
| `Promote(id)` | フェイルオーバー。消えた確定済み書き込みの数を返す |
| `Lag`/`Committed`/`LeaderOffset`/`ReplicaValue`/`LeaderValue` | 観測用 |

ネットワークや goroutine は使わず、明示的な操作で駆動する純粋なモデル。テストもデモも
決定的に再現できる(`distributed/raft` の `cluster.go` と同じ方針)。

## 簡略化したこと

- 複製は「モデル上は同期配送」— 到達可能なら `Write` の中で末尾まで流す。実物の非同期
  ストリーミング(遅延・順序保証・バックプレッシャ)は持たない。ラグは切断で表現する
- 永続化・ネットワーク・スナップショット転送は無し(状態は全てメモリ)
- リーダー選出はしない(`Promote` は手動)。合意で選ぶ話は [raft](../raft/) 側
- 分岐したログの解決は「新リーダーのログが正、長い側は切り詰め」の単純化(Raft と同じ発想)
