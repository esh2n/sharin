# leaderelection — 冗長化しつつ、同時に働かせない

コントローラは落ちる。落ちたら誰も調整しなくなるので、複数台で動かしておきたい。
だが複数台が同時に調整すると、同じ Pod を二重に作ってしまう。
冗長化はしたいが、同時に働いてほしくはない。

答えは、置き場に1つオブジェクトを作って、それを持っている者だけが働く形になる。
持ち主は定期的に更新し、他は更新が止まったのを見て奪う。

## 3つの時間と、その大小

| 設定 | 意味 |
|---|---|
| `LeaseDuration` | 変化を見なくなってから、他が奪ってよいと判断するまでの長さ |
| `RenewDeadline` | 持ち主が更新に失敗し続けたとき、自分から降りるまでの猶予 |
| `RetryPeriod` | 更新や奪取を試みる間隔 |

`RenewDeadline < LeaseDuration` でなければならない。降りるほうが先でないと、
奪われてから降りるまでの間、2人が同時に自分を持ち主だと思う。
実物の既定値は 15 秒 / 10 秒 / 2 秒で、`Default()` は同じ比を持つ。

```go
cfg := leaderelection.Default()   // 15 / 10 / 2
cfg.Safe()                        // true

s := leaderelection.New(cfg, "c1", "c2")
for i := 0; i < 7; i++ {
    s.Tick()
}
s.Partition("c1")                 // 持ち主が置き場に届かなくなる
for i := 0; i < 30; i++ {
    s.Tick()
}
s.Overlap // 0 ・ 2人が同時に持ち主だと思った時刻の数
s.Vacant  // 6 ・ 誰も持ち主でなかった時刻の数(安全にした代償)
```

`RenewDeadline` を 20 にすると `Overlap` が 4 になり、`Vacant` が 0 になる。
重なりと空位はどちらかしか消せない。

## 時計は共有できないが、経過は共有できる

待つ側は、持ち主が書いた時刻を読まない。他人の時計の値なので、自分の時計と
どれだけずれているか分からないからだ。代わりに `Version` の変化だけを見て、
「最後に変化を見てから自分の時計でどれだけ経ったか」で判断する。

そして観測が先、判断が後になっている。この順序でないと、切り離しから復帰した
候補が古い観測のまま「期限が切れている」と判断して、生きている持ち主から奪ってしまう。

## API

| 関数・メソッド | 役割 |
|---|---|
| `Default() Config` | 実物と同じ比の設定(15 / 10 / 2) |
| `(Config) Safe() bool` | 重なりが起きえない大小関係かを返す |
| `New(cfg, names...) *Sim` | 候補たちで選出を始める。名前順に行動する |
| `(*Sim) Tick()` | 論理時刻を1つ進める |
| `(*Sim) Holder() string` | 置き場のオブジェクトが誰のものになっているか |
| `(*Sim) Believers() []string` | 自分が持ち主だと思っている候補 |
| `(*Sim) Partition(name)` / `Heal(name)` | 置き場との切り離しと復旧 |
| `(*Sim) Overlap` / `Vacant` / `DoubleActs` | 重なり・空位・二重になった操作の数 |

## 決定性

実時間も乱数も使わない。候補は名前順に行動し、時計は `Tick` で1つずつ進む論理時刻。
切り離しは `Partition` で明示的に注入する。同じ手順なら必ず同じ結果になる。
