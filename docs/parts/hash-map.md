# ハッシュマップ

> 実装: [`data-structures/hashmap/`](https://github.com/esh2n/sharin/tree/main/data-structures/hashmap) / 実行: `go test ./data-structures/hashmap/`

<Summary>
Go の map、Python の dict、JS のオブジェクト。どれも正体は同じだ。キーをハッシュ関数で「バケット番号」に変換して、その1バケットだけ見るから平均 O(1) で引ける。ただし別のキーが同じバケットに落ちる衝突が避けられないので、その扱い方(チェイン法)と、詰まってきたらバケットを増やすリサイズが肝になる。
</Summary>

## この章で作るもの

`map[string]int` のような連想配列を自分で実装する。B-Tree が「順序を保つ木」で
`log n` だったのに対し、ハッシュマップは**順序を捨てる代わりに平均 O(1)** を得る。

この章の肝は3つ。

- キーをハッシュ関数で**バケット番号**に変え、その1バケットだけ見る。だから平均 O(1)
- 別のキーが同じバケットに落ちる**衝突**は避けられない。バケット内のリストで吸収する(チェイン法)
- 詰まってきたら(**負荷率**が上限超え)バケットを倍増して配り直す。
  これを怠ると O(1) が O(n) に劣化する

## バケットとハッシュ関数

配列の「何番目に置くか」をキーから直接計算できれば、1回のアクセスで済む。
そのための道具がハッシュ関数だ。キー(文字列でも整数でも)を数値に潰す関数である。
その数値をバケット数で割った余りが、置き場所(バケット番号)になる。

<FigureBox caption="キー → ハッシュ値 → バケット番号。同じキーは必ず同じバケットに落ちるので、探すときも1バケットだけ見れば済む">

```
"apple"  ──hash──▶ 8281...  ── % 8 ──▶ バケット 1
"banana" ──hash──▶ 4472...  ── % 8 ──▶ バケット 0
"cherry" ──hash──▶ 9915...  ── % 8 ──▶ バケット 3
```

</FigureBox>

## 衝突: 同じバケットに落ちたら

ハッシュ値は無限、バケットは有限。だから**別のキーが同じバケットに落ちる**ことは
必ず起きる(鳩の巣原理)。この章の**チェイン法**は、各バケットを「リスト」にして、
落ちてきた要素を並べる。Get はそのリストだけを線形に探す。

<FigureBox caption="チェイン法。バケット1に apple と grape が衝突しても、リストに並べて両方持てる。Get はこのリストだけ見る">

```
バケット0: [ banana ]
バケット1: [ apple ] → [ grape ]   ← 衝突。リストで吸収
バケット2: [ ]
バケット3: [ cherry ]
```

</FigureBox>

負荷率(件数 ÷ バケット数)が低ければ、各リストは平均1個ほど。だから Get は
「1バケット求めて、短いリストを見る」で平均 O(1)。逆に全部同じバケットに落ちると
リストが全要素分の長さになり O(n) になる。テストではこの最悪ケース
(ハッシュが常に同じ値)も固定してある。

## リサイズ: 詰まる前に広げる

要素を入れ続けると負荷率が上がり、リストが伸びて遅くなる。そこで**負荷率が
上限(この実装は 0.75)を超えたらバケット数を倍にして、全要素を配り直す**(rehash)。

<<< ../../data-structures/hashmap/hashmap.go#resize{go}

バケット数が変わると `% バケット数` の余りも変わるので、全要素の引っ越しが要る。
つまり **1回の resize は O(n)**。ハッシュマップは「普段は O(1)、たまに O(n) の
リサイズ」で、ならすと(償却して)O(1)。この「たまに重い」があることは、
レイテンシが気になる場面では知っておく価値がある。

**試す**: 追加していくと負荷率が上がり、0.75 を超えた瞬間にバケットが倍増して
(枠が光る)、要素が配り直される。最長チェインが伸びすぎず一定に保たれるのが見える。

## メリット / デメリット

**メリット**

- 検索・挿入・削除が平均 O(1)。順序が要らないなら B-Tree より速い
- 実装が単純

**デメリット**

- **順序がない**。範囲検索(`a〜c のキー`)やソート済み走査はできない([B-Tree](./btree)の出番)
- 最悪 O(n)(悪意ある衝突攻撃 = HashDoS。実物は乱数シード付きハッシュで防ぐ)
- resize が O(n) スパイクになる。リアルタイム用途では要注意
- ハッシュ関数の質に性能が依存する

**実例**

- Go の `map`(実際はバケットあたり8スロットのより凝った実装)、Python `dict`、Java `HashMap`
- Redis のハッシュ型、あらゆる言語の連想配列
- [ID Generation](./id-generation) で触れた「等価検索だけなら B-Tree よりハッシュが速い」の実体

## 簡略化したこと

- **チェイン法のみ**: 実物では**オープンアドレス法**(衝突したら別の空きバケットを探す)も
  多い。キャッシュ効率が良い一方、削除が面倒になる
- **ハッシュ関数は注入**: HashString(FNV) / HashInt を用意した。実物は型ごとに最適化し、
  HashDoS 対策の乱数シードも持つ
- **縮小しない**: 要素が減ってもバケットは減らさない
- **並行安全でない**: 実物のロック分割・`sync.Map` は扱わない
