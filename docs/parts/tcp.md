# tcp(信頼できるバイトストリーム)

<Summary>
下層の IP は、パケットを届く保証も順序の保証も無く運ぶだけで、落ちる・遅れる・入れ替わる。にもかかわらずアプリからは、書いた順にそのまま届く 1 本のバイトの管に見える。この錯覚を作るのが TCP だ。この章では、損失や並べ替えのある模擬網の上に、信頼できて順序どおりのバイトストリームを組み立てる。鍵は各バイトに振る通し番号、受信側が返す累積 ACK、返らないバイトの再送、送りすぎを防ぐウィンドウだ。
</Summary>

## この章で作るもの

ネットワークの下層(IP)は、パケットを**ベストエフォート**で運ぶだけだ。届く保証も、送った順に届く保証も無い。落ちるし、遅れるし、追い越しも起きる。ところがアプリが `write` したバイト列は、相手の `read` にそのままの順で、欠けずに届く。この落差を埋めるのが TCP で、信頼できない小包の集まりを、信頼できる 1 本のバイトストリームに見せる。

<FigureBox caption="TCP はベストエフォートの IP の上に、信頼できるバイトストリームの錯覚を作る。各バイトにシーケンス番号を振り、受信側は累積 ACK で『ここまで連続で受け取った』を返す。落ちたセグメントは再送で埋め、順序が乱れたら受信側が並べ替える">

```
   アプリから見た TCP           順序どおり・欠けなし
   write("HELLO TCP") ──────────────────────────▶ read("HELLO TCP")

   TCP が下でやっていること(seq を振り、ACK で確認、抜けを再送)
   seq101 "HELL"  ──▶ ack105
   seq105 "O TC"  ──✗ 落ちた
   seq109 "P"     ──▶ (ack は 105 のまま=穴。受信側は退避)
   seq105 "O TC"  ──▶ ack110  再送で穴が埋まり、まとめて確定
   ─────────────────────────────────────────────
   IP: ベストエフォート(落ちる・遅れる・入れ替わる)
```

</FigureBox>

肝は3つ:

1. **信頼性 = seq + ACK + 再送**: 番号で「どこまで届いたか」を突き合わせ、抜けたら送り直す
2. **順序 = 受信側の並べ替え**: 累積 ACK は連続の先頭までしか進まない。隙間が埋まるとまとめて渡す
3. **フロー制御 = ウィンドウ**: 相手が受け取れる量を超えて送らない

肝心なのは、SYN と FIN もシーケンス番号を 1 つ消費することだ。制御イベントをデータと同じ番号空間に置くから、「SYN が確かに届いた」「送信終了が確かに届いた」を、データと同じ ACK の仕組みで確認できる。3-way ハンドシェイク(SYN → SYN-ACK → ACK)は、この番号を両者で同期させる儀式だ。

## ③ 順序: 累積 ACK と並べ替えバッファ

受信側。届いたセグメントを、順序を見て処理する。期待する番号(`rcvNxt`)ちょうどならアプリへ渡して `rcvNxt` を進め、退避してあった続きも連続する限り取り込む。先走って届いたら並べ替えバッファ(`ooo`)へ退避する。累積 ACK は `rcvNxt` のままなので、送信側は抜けを送り直してくれる:

ここに TCP の順序保証の本質がある。累積 ACK は「連続して受け取った先頭」までしか進めない。だから抜けが 1 つあると、その後がいくら届いても ACK は進まず、送信側は必ず抜けを埋め直す。受信側は先行分を捨てずに退避しておくので、穴が埋まった瞬間にまとめてアプリへ渡せる。落ちる・遅れる・入れ替わる網の上で、書いた順のバイトストリームが復元される。

下のデモは、この TCP を**そのままブラウザで**動かしている。クライアントがサーバへ短いメッセージを送る。「セグメントを落とす」を選ぶと特定のパケットが失われ、「1手すすめる」で 1 ステップずつ——**ハンドシェイク → データ転送 → 落ちたセグメントの再送 → 順序の復元**を追える。累積 ACK が穴の手前で止まり、再送で穴が埋まると一気に進む様子が見えるはずだ。

## 設計の観点: TCP の設計と使いどころ

- **信頼性の 3 点セット**: シーケンス番号(順序と重複検出)・ACK(到達確認)・再送(損失回復)。この 3 つで「信頼できる順序ストリーム」が成り立つ。どれが欠けても壊れる
- **累積 ACK vs 選択的 ACK(SACK)**: 素の TCP は累積 ACK で「ここまで連続」しか伝えられず、1 つの損失で後続の再送が無駄になりうる。SACK は「飛び飛びに受け取った範囲」も伝え、必要な分だけ再送できる。実運用ではほぼ SACK が使われる
- **フロー制御 vs 輻輳制御**: ウィンドウには 2 種類ある。**フロー制御**(相手が受け取れる量=広告ウィンドウ)と**輻輳制御**(網が詰まっていないか=cwnd、スロースタート/輻輳回避)。前者は相手を守り、後者は網を守る。本章はフロー制御まで
- **ハンドシェイクのコスト**: 3-way は 1.5 往復かかる。短い通信ではこれが無視できない。だから TCP Fast Open や、UDP 上に信頼性を再構築した **QUIC**(0-RTT・多重ストリーム・ヘッドオブラインブロッキング回避)が生まれた
- **いつ TCP を使わないか**: 順序保証のせいで 1 つの損失が後続を止める(ヘッドオブラインブロッキング)。低遅延・多重化が要る動画会議やゲームは UDP や QUIC を選ぶ。順序と信頼性が要るファイル転送・HTTP は TCP

この章の要点は「TCP は seq+ACK+再送で信頼性、累積 ACK と並べ替えで順序、ウィンドウでフロー制御を作る。輻輳制御は別レイヤ。ハンドシェイクとヘッドオブラインブロッキングが弱点で、QUIC はそこを UDP 上で解く」に尽きる。

## メリット・デメリットと実例

| プロトコル | 信頼性/順序 | 遅延 | 多重化 | 実例 |
|---|---|---|---|---|
| TCP | ◎(順序保証) | △(ハンドシェイク+HoL) | ✕(1 ストリーム) | HTTP/1.1・HTTP/2、SSH、DB 接続 |
| UDP | ✕(自前で回復) | ◎(即送る) | —(アプリ次第) | DNS、動画/音声、ゲーム、QUIC の土台 |
| QUIC | ◎(ストリーム毎) | ◎(0-RTT) | ◎(多重・HoL 回避) | HTTP/3、YouTube、多くの CDN |

裏どり:

- **HTTP/2 と HoL ブロッキング**: HTTP/2 は 1 本の TCP 上で複数リクエストを多重化したが、TCP が 1 つ損失すると**全ストリームが止まる**(TCP レベルの HoL)。これが HTTP/3=QUIC への移行動機
- **QUIC**: Google 発、UDP 上に TCP 相当(+TLS)を再実装。ストリームごとに独立した順序保証なので、あるストリームの損失が他を止めない。接続確立も速い(0-RTT)。HTTP/3 の土台
- **DNS が UDP な理由**: 問い合わせ 1 発・応答 1 発で終わるなら、ハンドシェイクのコストを払う TCP より UDP が軽い(大きな応答や信頼性が要る場合は TCP にフォールバック)
- **SACK は標準装備**: 現代の TCP(Linux 等)はほぼ SACK 有効。累積 ACK だけの再送効率の悪さを、受信範囲を細かく伝えることで補っている

## 簡略化したこと

- **輻輳制御なし**: スロースタート・輻輳回避(cwnd)・高速再転送/回復は無し。ウィンドウは相手の広告値(フロー制御)のみ
- **固定 RTO**: RTT 計測に基づく適応タイムアウト(Karn/Jacobson)は無し。再送は固定ステップで判定
- **データは一方向**: クライアント→サーバの転送に絞る(ハンドシェイクとクローズは両方向)
- **累積 ACK のみ**: SACK(選択的確認応答)は実装しない(対比として設計の観点の節で説明)
- **チェックサム・ポート/IP・実ヘッダなし**: 誤り検出・多重化(ポート)・実際のヘッダ整形は扱わない。信頼性・順序・フロー制御の骨格だけ
