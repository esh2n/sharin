# cqrs — コマンドとクエリの責務分離

書き込み(コマンド)と読み取り(クエリ)を別のモデルに分ける。書き込み側はイベントを流し、読み取り側は同じイベントから用途別の読みモデル(射影)を組む。中心は「1 つのイベント列から複数の読みモデル」と「結果整合」を示すこと。

## 肝

- **責務の分離**: 書きは正しさ(検証・整合性)、読みは速さと使いやすい形。1 つのモデルで両立しようとすると中途半端になる
- **書き込み側(コマンド)**: 状態を検証してからイベントを流す。無い注文の支払い、支払済みの取消などを拒否
- **読み取り側(クエリ)**: 同じイベントを畳んで射影を作る。注文状況・顧客ごとの購入額・総売上を、それぞれ独立に
- **1 イベント列 → 複数ビュー**: 用途ごとに最適な形の読みモデルを、同じイベントから何個でも
- **結果整合(eventual consistency)**: 読みモデルは書きに少し遅れて追いつく(CatchUp)。その間は古い値を返す。これが分離の代償

## 効果の固定(テスト)

- `TestMultipleProjections`: 同じイベントから状態一覧・顧客購入額・総売上の 3 射影を同時に構築
- `TestWriteValidation`: 重複作成・二重支払い・支払済みの取消を拒否
- `TestEventualConsistency`: 書き込み直後は読みモデルが遅れ(Lag)、CatchUp で追いつく

## 使い方

```go
var s cqrs.Store
w := cqrs.NewWriteSide(&s)
r := cqrs.NewReadSide(&s)

w.Place("o1", "alice", 1000) // コマンド(検証してイベントを流す)
w.Pay("o1")

r.CatchUp()          // 読みモデルを最新に(それまでは古い)
_ = r.Status["o1"]   // 注文状況ビュー
_ = r.Spend["alice"] // 顧客ごとの購入額ビュー
_ = r.Revenue        // 総売上ビュー
```

## 簡略化したこと

- **同期の CatchUp**: 実物は読み側が非同期にイベントを購読する。ここは明示的に呼ぶ
- **単一プロセス**: 書きと読みが同じメモリ。実物は別サービス・別 DB(書きは正規化、読みは非正規化)
- **イベントソーシング前提でない**: CQRS はイベントソーシング必須ではないが、ここでは併用([event-sourcing](/parts/event-sourcing))
- **並行制御なし**: 同時コマンドの競合は扱わない
