# scheduler — M:N スケジューラと work-stealing

Go ランタイムがどうやって数百万の goroutine を数個の OS スレッドで回すか——
その心臓部である **M:N スケジューラ(GMP モデル)と work-stealing による負荷分散**
——を Go でモデル化する。ランタイム内部編のパーツ。実スレッドを使わず、複数の
プロセッサが仕事を均していく様子を決定的に再現する。

教科書の章: [scheduler](https://sharin-2a1.pages.dev/parts/scheduler)

## これは何か

[os 編](../os)の協調スケジューラは **CPU 1 個・実行キュー 1 本**だった。だが実機は
コアが複数ある。素朴に「キュー 1 本を全コアで共有」すると、その 1 本のロックが
ボトルネックになる。かといって「コアごとに独立キュー」にすると、仕事が偏ったとき
暇なコアが遊ぶ。Go ランタイムの答えが **M:N + work-stealing** だ。

- **GMP モデル**: **G** = goroutine(走らせたい仕事)、**M** = OS スレッド、
  **P** = プロセッサ(スケジューリング文脈。ローカル実行キューを持つ)。M は P を
  1 つ握らないと G を走らせられない。P の数(`GOMAXPROCS`)が並列度を決める
- **ローカルキュー**: 各 P が自分の実行キューを持つ。G の出し入れに毎回グローバルな
  ロックを取らずに済むので、コアが増えてもスケールする
- **work-stealing**: ある P のローカルキューが空になったら、まずグローバルキューを見て、
  それも空なら**他の P からキューの半分を横取り**する。これで偏りが自動的に均される

```
        P0                    P1                    P2
   ┌─ local ─┐           ┌─ local ─┐           ┌─ local ─┐
   │ G G G G │           │ (空)    │  ◀─steal──│ (空)    │
   └────┬────┘           └─────────┘   half    └─────────┘
        │ 偏り!                ▲___________________|
        └── P1 が半分を横取り ──┘   暇な P が忙しい P から仕事を盗む

        ┌──────────── global run queue(全 P 共有)────────────┐
        │  ローカルが溢れたぶんの G / 新規のあふれ           │
        └────────────────────────────────────────────────────┘
```

## 肝は3つ

1. **P ごとのローカルキュー**: 仕事は基本、生成した P のローカルキューに積む。
   ローカルなのでロック無しで速いが、そのぶん偏りやすい
2. **work-stealing で均す**: 空になった P は、他の最も混んでいる P からキューの半分を
   盗む。「半分」なのは、盗みすぎず・盗まなさすぎずのバランス(次も盗まれる側に残す)
3. **グローバルキューとあふれ**: ローカルが上限に達したら半分をグローバルへ退避
   (spill)。暇な P はグローバルからも引く。これがもう 1 つの負荷分散経路

## ファイル

- `goroutine.go` — `G`(goroutine: 必要な仕事量 `work`)と `P`(プロセッサ: ローカル
  キュー・実行量・横取り回数)。`State`(runnable/running/done)
- `scheduler.go` — `Scheduler`。`Go`/`GoOn`(生成)、`Step`(1 ラウンド = 全 P が 1 量子
  ずつ進む)、`steal`(横取り)、`fromGlobal`(グローバルから引く)、`Run`、観察用ビュー

## 設計メモ

- **ラウンド制で並行を表す**: 1 回の `Step` で全 P が同時に 1 量子進む、というモデルに
  して並列実行を決定的に扱う。P は index 順に処理するので、同じ入力なら常に同じ結果
- **決定的な横取り**: 盗む相手は「最も混んでいる他の P(同数なら index 最小)」。乱数は
  使わない。実機の Go は乱数で相手を選ぶが、ここでは再現性を優先
- **協調的プリエンプション**: `quantum` を使い切ると、まだ残る G はローカルキューの末尾へ
  戻す。os 編の yield に当たる切り替え点(実機はこれに加え非同期プリエンプションを持つ)
- **負荷分散の指標**: 各 P の実行 tick(`Ran`)が揃っていれば、偏った投入でも均せた証拠

## 簡略化したこと

- **M(OS スレッド)は省略**: 「P 1 つにつき常に M が 1 つある」前提。syscall で M が
  ブロックしたとき P を別の M に渡す(handoff)・spinning M・M の生成/破棄は扱わない
- **横取りは決定的**: 実機はランダムな P から盗み、複数回試す。ここでは最混雑 P 固定
- **グローバルキューの定期チェック省略**: 実機は約 61 回に 1 回グローバルを優先して見て
  グローバルの飢餓を防ぐ。ここではローカルが空のときだけ見る
- **仕事は tick 数**: G は「実際の計算」をせず、`work` tick を消費し切ったら終了。I/O 待ちや
  チャネル待ちでのブロックは扱わない
- **`GOMAXPROCS` 固定・ネットワークポーラ無し**: P 数は生成時固定。epoll 連携は
  [event-loop 編](../eventloop)を参照
